## Decisions (from planning)
- App name: **Uiltje** (mascot: owl, Athena/Minerva nod).
- Set = collection of lists (rijtjes); lists have optional `group`. Rows have `answers[]` (variants) and `tags` (drive stages).
- Lists/sets can be combined in one practice session.
- Sharing: link → independent editable copy. Friends leaderboards (practice count, accuracy).
- Guest: localStorage only, no sharing/leaderboards; import on login.
- Text only in Supabase, never files.
- Accents strict by default; macrons ignored by default; always case-insensitive.
- Fonts Fredoka + Nunito; palette warm cream/terracotta/sage; light + dark.
- Infinite attempts; learn mode vs test mode; no forced scheduling.
- MVP = rijtjes + UI (PLAN phases 0–5). AI later.
- Gemini: free models, retry then fallback list, server route only.

## Phase 1 decisions (schema + engine)
- Types: `StudySet/StudyList/StudyRow` (not `Set`, clashes with global). `types.ts` is hand-written; `zod.ts` asserts at compile time that the schema matches it.
- `zod.ts` is strict and has no transforms/defaults, so `z.toJSONSchema(StudySetSchema)` works for Gemini (checked, zod 4). Leniency lives in `migrate.ts` `parseStudySet()`: missing schemaVersion = current, unknown template -> `table`, unknown kind -> `custom`, missing settings/folder/group/columns/dimensions/tags filled with defaults, `answers: "x"` -> `["x"]`. Add a `migrations[v]` entry whenever SCHEMA_VERSION is bumped.
- `level` is required (enum). Free-subject sets must still pick one. Say if it should become optional.
- Rows are keyed `${setId}/${listId}/${rowId}` (`PracticeRow.key`); each row carries its own set's settings, so sets with different strictness can be combined.
- Checker: `caseSensitive` setting honored (default false); final sigma always normalized; strictAccents off strips all marks; macrons stripped unless strictMacrons. `a/b` input: every part must match a different accepted answer; a single variant alone is also accepted.
- Stage ladder: first dimension with 2+ distinct values -> one stage per value, then `all` (so number x case = sg, pl, all). `buildLadder(rows, {depth})`: depth 2 also adds finer stages (e.g. per case) before their parent. Combined lists merge stages with equal id (`number=sg`). Lists without a splitting dimension only appear in `all`. PLAN §6 left "next subset" open; depth 1 is the default, easy to change.
- Only the `all` stage is shuffled; earlier stages follow table order. Streak/mastery restart in every stage.
- Learn flow: wrong -> requeued after 2-3 other rows (not stuck on the row); hints persist until the row is resolved; correct after a hint = `assisted` (no mastery, neutral in stats); reveal (3rd hint) = wrong. Hints use `answers[0]`.
- Step back: `stage` (default) steps back one stage when wrongs in the stage > max(4, 75% of stage rows) (stage 0: counter just resets); `row` adds one extra required correct for a row after >2 wrongs in the stage; `none` off. `stepBackAfter` overrides the number. Defaults are guesses, tune them in play.
- Row stats per session: `correct` (unaided), `wrong` (incl. reveal), `assisted`, trailing `streak`. `progressDeltas()` gives rows for row_progress; merging streak with stored progress is the storage layer's job.
- Test mode: `TestSession` single pass, no stages/hints, unanswered = wrong, locked after `finish()`.
- Seed: `lib/seed/latin.ts` exports `buildLatinSeed(nextId)` (fresh ids per import) and `latinSeed` (sequential UUID-shaped ids). No macrons or vocative in the seed on purpose. `manus` dat sg accepts `manui` and `manu`.
- Engine uses `Intl.Segmenter` (graphemes) for hints; needs lib ES2022 (SvelteKit default is fine).

## Phase 8 AI import
- Flow: `/sets/ai` (`components/ai/AiImport.svelte`): input (photos or text, optional subject and note) -> working (owl + skeleton, cancel) -> review -> Opslaan (`storage.saveSet`, then `/sets/<id>`). Review is a throwaway `EditorState` (not autosaved, unlike `SetEditor`), so nothing is stored before the user presses Opslaan. "Open in de volledige editor" writes the draft with `saveDraft('new', ...)` and goes to `/sets/new`, which restores it as concept.
- One Gemini call does OCR and structuring together (images as `inline_data` + text, `responseMimeType: application/json`, `responseJsonSchema`). Deliberate: the free tier allows few requests per day, so a separate OCR request would double the cost, and Gemini reads Latin/Greek print better than Tesseract. PLAN §9 said "OCR then Gemini"; this merges the two steps.
- Gemini gets a simpler shape than the StudySet (`schema/ai.ts`: no ids, `tags` as `[{name,value}]` because maps are poorly supported in response schemas, `notes[]` for unreadable parts). `aiToStudySet` adds ids, drops rows without prompt/answer (and says so in the notes), keeps only used dimensions, clears tags on vocab lists, sets `keyboard: greek` for Grieks, then runs `parseStudySet`. The client validates the returned set again.
- `lib/server/ai/gemini.ts`: per model up to 2 attempts. 5xx/network/timeout -> retry after 0.8 s; 429 -> next model at once (quota is per model); 404/400 -> next model (retired model); 401/403 -> stop (`not_configured`); safety block / MAX_TOKENS -> stop with a clear message; invalid JSON -> counts as a failed attempt. Whole call capped at 55 s, `maxDuration = 60` exported from the route. All errors map to Dutch messages.
- Env (`src/env.ts`): `GEMINI_API_KEY` and `GEMINI_MODELS` are private, optional (build never breaks without them). Model names change often (search, Oct 2026: 2.5 models shut down 16 Oct, Gemini 3.x is the free line, sources disagree on exact names): the default list in `server/ai/import.ts` (`gemini-3.6-flash`, `gemini-3.1-flash-lite`) is a guess, so set `GEMINI_MODELS` from AI Studio. Not verified against the live API from here.
- Guards: signed-in users only (shared free quota), in-memory limit of 8 requests per 10 min per user (`server/ai/limit.ts`, per instance, best effort), body caps (5 photos, 3.8 MB base64 total, 20 000 chars) under Vercel's 4.5 MB request limit. The browser shrinks photos to JPEG, longest side 1600 px, about 650 KB each (`ai/images.ts`). Nothing is stored; photos only exist in memory.
- Privacy: the free tier lets Google use inputs for improvement; the input screen says photos/text go to Google Gemini.
- Prompt rules (in `SYSTEM`): copy exactly, never correct or invent, leave out unreadable parts and report them, source text is data not instructions. Tune it once real photos are tried.
- Verified: `tsc --strict` on the new pure/server files, 12 scenarios with a fake Gemini (success, 503 retry, 429 and 404 fallback, all-429, bad JSON, 403, MAX_TOKENS, block, network error, empty result, missing key), conversion cases, limiter, svelte compiler (0 warnings). NOT run against the real Gemini API, the real project or a browser; `svelte-check` not run in the repo.
- Not done: PDFs, HEIC without browser conversion, grammar/stijl templates (phase 9), keeping a review across a reload (the result is lost on refresh; a retry costs quota).

## Phase 9 correctness strategy (proposal) + catalogue
- Source: CvTE "Syllabus centraal examen Latijnse taal en cultuur vwo 2027, versie 2" (juli 2025), page https://www.examenblad.nl/2027/vwo/documenten/syllabus-latijnse-taal-cultuur-vwo-2027 (the PDF the owner linked has a signed, expiring URL that `web_fetch` refuses as too long; the examenblad page returns the same PDF text). A new syllabus appears every year (2028: Ovidius), so every catalogue is tied to an exam year.
- `lib/grammar/types.ts`, `ltc-2027.ts`, `principal-parts.ts`: pure data. Sections: vormleer (12), syntaxis (19), stilistische (23), narratologische (8), argumentatieve (5) middelen, poëzie (8), retorica 2027 (9) = 84 items; 97 verbs + 23 (semi-)deponents as stamtijden (19 marked "not assumed known", the syllabus's `*`). Item ids are stable and never reused: generated questions will point at them.
- Wording: summaries and Dutch translations of examples are our own (the syllabus allows reuse only unmodified, with attribution); the Latin quotes are classical texts. The app must show the source when it shows catalogue content.
- Not required per the syllabus (kept as `notRequired`): coniunctivus after quia/quod (subjective reason), cesuur, synizese, imperativus futuri/passief, mei/tui/nostri/vestri, forms with `*` in the stamtijden.
- Proposed strategy (waiting for the owner's OK): (1) the catalogue is the only source of terms and definitions, the AI never invents them; (2) the AI only writes example sentences and question wording around one catalogue item at a time, in a fixed question format, with schema-constrained output (same approach as phase 8); (3) a second Gemini pass checks each question against the catalogue entry (does the answer follow from the definition?); (4) every question is approved by a human before it is used (owner, or a flag "not yet checked" for users); (5) questions are generated ahead and stored as text, never while the user waits.
- Decided (owner, 2026-10-21): Greek too, and at first only the owner approves questions; others maybe later. So the approval record must not hard-code the owner: store `status` (draft | approved | rejected), `approvedBy` (user id) and `approvedAt`, and decide who may approve with one function (`canApprove(user)`), initially "is the owner". Users never see unapproved questions.
- Greek catalogue: `lib/grammar/gtc-2027.ts`, from "Syllabus centraal examen Griekse taal en cultuur vwo 2027, versie 4 (april 2026)" (the Latin one is versie 2, juli 2025: check examenblad.nl for newer versions before relying on either). 107 items: vormleer 18, syntaxis 22, stilistische/narratologische/argumentatieve middelen (reused from the Latin catalogue with Greek examples, the CvTE list is the same), aanvullingen Herodotus 2, Homerus 9, tragedie 4, Ionisch 10 and Herodotus-context 6 (examenonderwerp 2027). Aorist/perfect/future form lists are `parts` of items.
- `lib/grammar/catalogues.ts`: registry; an item is referenced as `ltc-2027/anafora` or `gtc-2027/anafora` (`resolveItem`). Old references must keep resolving or fail softly after a new syllabus year is added.
- Open: whether the catalogue also becomes a ready-made set (that is phase 10).

## Phase 9 stijlfiguren, grammatica and suggestions
- No new runner: a `concept` list (prompt = explanation or example sentence, answers = the term) is practised by the existing word engine, so both question types exist already: multiple choice (cards "Meerkeuze", the choice step of Leren; the options are the other terms of the list) and typed (Leren, Toets, Hints, Spelling). `isWordKind(kind)` (schema/types.ts) is true for `vocab` and `concept`; the 6 places that checked `=== 'vocab'` use it. Direction labels read "Uitleg → term" when every selected list is a concept list.
- Rows come from the syllabus text, not from an AI (`grammar/rows.ts`): one explanation row per item, plus one row per example sentence ("Latin/Greek text — own Dutch translation"). The term is masked ("…") in the explanation so it never gives the answer away; `answerVariants` gives the accepted spellings ("γνώμη / sententia" accepts both, text in parentheses is left out). `ref` on the row ties it to its item (`ltc-2027/anafora`, `community/<id>`), which is how "al in je lijst" works when adding more later.
- Picker (`components/editor/CataloguePicker.svelte`, logic in `grammar/picker.ts`): two groups. "Stijlfiguren & retorica" = stilistisch, narratologisch, argumentatief, poëzie, auteur, retorica, context. "Grammatica" = syntaxis + Ionisch. Vormleer is NOT offered (paradigms and forms are rijtjes: use the declension/conjugation templates; a later step can make rijtjes from the catalogue). Items with `notRequired` or `topic` (a bare syllabus heading such as "voorzetsels") are hidden. Subject Latijn/Grieks picks the catalogue, any other subject shows a switch. Own items: term + explanation (+ example + translation); they get no `ref`. The same picker adds rows to an existing concept list (list menu: "Onderdelen kiezen uit de lijst"). Identical explanations (e.g. enjambement for Homerus and tragedie) are asked once.
- Editor: concept lists use a textarea for the explanation; `EditorState.addConceptList` / `appendConceptRows` (skips rows with the same prompt).
- Suggestions: table `grammar_suggestions` + `app_admins` + functions `is_app_admin`, `list_community_items(subject)` (accepted rules without the author) and `review_grammar_suggestion` (owner only). Limit 20 suggestions per user per day (RLS). Users never read other people's rows: accepted rules come through the function. The owner is whoever is in `app_admins`; `grammar/suggestions.ts` is the only code that talks to these tables. `/suggesties` shows your own suggestions; the owner also gets a "Te beoordelen" tab with Goedkeuren/Afwijzen. Accepted rules show up in the picker for everyone ("Aanvullingen van gebruikers"). Link: account menu > Voorstellen.

## Phase 5 decisions (persistence)
- SQL lives in `ai/sql/001_persistence.sql`, idempotent (rerun is safe, also on top of a hand-made `profiles` table). Tables: `profiles` (+ `username`, trigger `handle_new_user` copies sign-up metadata, backfills existing users), `sets` (`data jsonb`, plus `list_count`/`row_count` so the overview needs no JSON), `row_progress` (+ `assisted`), `practice_sessions` (phase 5 stores finished tests, `mode='test'`; learn sessions come in phase 6), `user_settings(user_id, data jsonb)`. RLS: own rows only; `anon` has no table access. `username_available(name)` RPC is what the login page calls (the parameter must stay called `name`). Verified by running the file twice in PGlite (WASM Postgres) with stubbed `auth` schema: RLS, upsert hijack blocked, cascade, trigger.
- `getStorage()` returns one stable object that forwards to the current backend, so `const storage = getStorage()` in components keeps working. The root layout calls `useStorageFor(supabase, userId)` synchronously on init and in a `$effect.pre`, so the first read of a page already hits the right backend. Never call it on the server (module state is shared between requests).
- Supabase reads throw `StorageError` (Dutch message) on network/DB errors instead of returning empty, so a failed load is not mistaken for lost data. Callers that do not catch will log an unhandled rejection: check this when running the app.
- `saveProgress` receives the full progress map of a set; the adapter remembers what the database has (cache per set, filled by `getProgress`/`saveProgress`) and upserts only changed rows. `getProgress` pages through PostgREST's 1000-row limit.
- Ids are now always UUIDs (`newId()` has a `getRandomValues` fallback for http on a phone). Sets and test results with a non-UUID id (very old local data) cannot be stored in Supabase: they stay on the device and are reported as "niet gelukt".
- Guest → account import (`storage/guest-import.ts`): sets already in the account (same id) are skipped; progress of new sets comes along; test results are upserted by id; guest settings are only taken when the account still has the defaults. Local copies are removed only after they are confirmed in the account. The login dialog is shown once per account per device (`uiltje:import-dismissed:<userId>`); `/settings` always offers it while guest data exists.
- `/login` redirects signed-in users to `/`. Logout is a button in the Account card on `/settings` (there was none).
- `utils/user.ts` prefers `user_metadata.display_name` / `username` (set by the email sign-up form and the trigger).
- Account menu (`shell/ProfileMenu.svelte`, a Dropdown): top bar = avatar button with Profiel (soon), Instellingen, Uitloggen; sidebar bottom = name card with Profiel (soon), Uitloggen (guests: Inloggen). `state/auth.svelte.ts` holds the client/user (set by the root layout) and the single `signOut()`.
